<objective>
Make `template_match_counts` (the shared counter behind `ts_stats` Pincus approximate entropy and `ts_features` sample_entropy / approximate_entropy) sub-quadratic for long series while returning EXACTLY the same counts as today (#304). The approach is fixed by the orchestrator's locked design: map values to ranks, turn each template's Chebyshev-ball match set into an integer box in rank space, then count points in boxes exactly. m=2 uses an offline 2D sweep with a Fenwick tree. m=3 uses CDQ divide-and-conquer for 3D dominance with memory-bounded passes. Everything else falls back to the unchanged band search.

Exactness facts the executor must honor. The planner verified these, so do not re-derive them:
- Today's coordinate-0 match predicate is the band prefilter AND the abs check: `!(v < a - r) && v <= a + r && (a - v).abs() <= r`. It is NOT equal to the abs check alone. Verified counterexample: a = 1.0, v = -1e-17, r = 1.0. Here `v < a - r` is true, so the band excludes v, yet `(a - v).abs()` rounds to exactly 1.0 <= r. The reverse query (a = -1e-17, v = 1.0) is accepted. The relation is therefore asymmetric. An abs-only fast path would NOT be bit-identical.
- Coordinates 1..m-1 use only `(a - v).abs() <= r`, where a is the query template's value and v is the candidate's value. Use that exact expression in the partition predicates, so the result does not depend on any sign-symmetry argument.
- For finite a and finite r >= 0, both predicates hold for v = a. Each is a conjunction of conditions that are monotone in v (IEEE rounding is monotone), so each match set is a contiguous run of the sorted, deduplicated value array.

Implement locked design step 5 in template_match.rs: `pub(crate) fn count_m3(x: &[f64], r: f64) -> Vec<usize>`, which delegates to `fn count_m3_with_pass_cap(x: &[f64], r: f64, max_items_per_pass: usize) -> Vec<usize>` using a module `const MAX_CDQ_ITEMS_PER_PASS` of about 8 million.

Model:
- Points j in 0..n_m (n_m = n - 2) are (rank[j], rank[j+1], rank[j+2]).
- Query i has a-range [lo0[i], hi0[i]] (the first-coordinate band-aware interval from Task 1), b-range [lo[i+1], hi[i+1]] and c-range [lo[i+2], hi[i+2]] (pred_abs intervals).
- Use inclusion-exclusion over (a, b): four corner families (hiA, hiB, +1), (loA-1, hiB, -1), (hiA, loB-1, -1), (loA-1, loB-1, +1). Skip any corner whose a or b coordinate would be negative.
- Answer c with a Fenwick range query over [c_lo, c_hi]. This folds the 8 corners of the locked design into 4 items with a range query. The counts are identical, and the CDQ input is half as large.

Item layout: a `#[derive(Clone, Copy)]` struct of five u32 (a, b, c_lo, c_hi, tag), 20 bytes. tag is either a POINT sentinel, or a query's template index with a sign bit. Points set c_lo = c.

CDQ:
1. Sort the pass's items by key (a, is_query), so points come before queries on ties. Use a counting sort over a, or `sort_unstable_by_key` on `(a as u64) << 1 | is_query`.
2. Recurse solve(lo, hi) with one reusable scratch buffer. Small leaves may use exact pairwise counting below a cutoff (executor's choice).
3. After both halves return sorted by (b, is_query), walk the right-half queries in that order. Insert left-half points with b <= q.b into the Fenwick at c, then add sign * fenwick.range(c_lo, c_hi) to the i64 accumulator of q's template.
4. Undo exactly the inserted points with add(c, -1). Never clear or reallocate the Fenwick per call.
5. Merge the halves by (b, is_query) through the scratch buffer.

Why this is correct: the (a, point-first) order guarantees that every left-half point has a <= every right-half query's a. A query never precedes an equal-a point, so the a-dimension is handled by position, and the b-dimension is handled by the merge two-pointer.

Recursion depth is about log2(items), at most 26 here, so recursion is safe.

Memory-bounded passes (locked step 5): each pass holds the n_m points plus the queries of a subset of the 4 corner families. Pick families-per-pass as the largest of {4, 2, 1} such that n_m * (1 + families) <= max_items_per_pass, with a floor of 1 family. Accumulate into one i64 array across passes. This bounds peak memory for multi-million-row pooled series. Document the per-row byte cost in a comment.
