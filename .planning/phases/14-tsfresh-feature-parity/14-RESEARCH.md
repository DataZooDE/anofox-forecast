## Summary

The 117 names in `list_features()` (`crates/anofox-fcst-core/src/features.rs:327-432`) break into three buckets after reading the pinned tsfresh 0.21.2 source (`validation/reference/python/.venv`, confirmed via `uv run --locked`) against the current Rust implementation:

1. **Already correct, no change** (≈35 names) — `abs_energy`, `root_mean_square`, `mean_change`, `mean_abs_change`, `absolute_sum_of_changes`, `cid_ce`, `c3_lag*`, `large_standard_deviation`, `ratio_beyond_r_sigma_*`, `count_above_mean`/`count_below_mean`, `first_location_of_maximum`/`minimum`, all basic stats, all `has_duplicate*`/reoccurring-value features, `variation_coefficient`. Verified by deriving the exact tsfresh formula from source and confirming the current Rust code is algebraically identical. These still belong in the mapping file (as "confirmed match, no fix needed") so the 117/117 parity test covers them too.
2. **Confirmed broken, with the exact missing term now identified** (the audit's F1–F11, ≈15 names) — `partial_autocorrelation_lag3..5`, `mean_second_derivative_central`, `last_location_of_maximum`/`minimum`, `time_reversal_asymmetry_stat_*`, `fft_coefficient_*` (normalisation + O(n²) DFT), `spectral_centroid`/`spectral_variance` (two-sided vs one-sided), `agg_linear_trend_rvalue` (sign), `skewness`/`kurtosis` (population vs bias-corrected — shared with Phase 13 D-05), `sample_entropy`, `binned_entropy`, `benford_correlation`, `permutation_entropy` (normalisation), `lempel_ziv_complexity` (wrong algorithm), `number_peaks` (support semantics TBD by fixture).
3. **A NEW finding beyond the audit's F1–F11** — `autocorrelation_lag1..10` normalises by the *whole-series* sum of squared deviations (`Σ(xᵢ-μ)²` over all n terms) instead of tsfresh's `(n-lag)·var(x)` denominator. Verified numerically against the live tsfresh calculator (reproduced below) — a 30-point series gives `lag1: ours=-0.0900 vs tsfresh=-0.0931`, a real, non-trivial mismatch that the F1–F11 audit list did not catch. This needs the same fix treatment as the F-series findings.
4. **No tsfresh counterpart at all** (`range`, `first_value`, `last_value`, `zero_crossing_rate`, `percentage_above_mean`, `count_unique`, `number_peaks_threshold_1`/`_2`, `linear_trend_r_squared`) — confirmed by checking tsfresh's full calculator list; these get a direct numpy/scipy reference per D-02. One of these, `zero_crossing_rate`, is itself a NEW finding: tsfresh's closest calculator (`number_crossing_m`) returns a raw *count* at an arbitrary threshold `m`, not a *rate* over `n-1` with exact-zero exclusion — there is genuinely nothing to match against; the mapping must say so explicitly rather than silently picking `number_crossing_m(m=0)` and calling it parity.

**Primary recommendation:** Generate the tsfresh side of every fixture by calling `tsfresh.feature_extraction.feature_calculators.<fn>(x, <exact params>)` directly — **not** `tsfresh.extract_features(df, default_fc_parameters=...)`. Many of this project's exact parameter choices (`agg_linear_trend` chunk_len = `n/10`, `approximate_entropy`/`sample_entropy` r = 0.2, `lempel_ziv_complexity` bins) do **not** appear in tsfresh's `ComprehensiveFCParameters` default grid at all (confirmed below), so the convenience API would silently compute the wrong parameter combination or omit the feature. The mapping file's job is precisely to pin, per feature, which calculator *and* which exact parameter values apply — then the generator script calls that exact function signature.

All quotes below are from `tsfresh.feature_extraction.feature_calculators`, read via `uv run --locked --project validation/reference/python python -c "import tsfresh, inspect; ..."` this session (`[VERIFIED: tsfresh==0.21.2 installed source]`). ### PACF (Durbin-Levinson) — FEAT-01

tsfresh's `partial_autocorrelation(x, param)` calls statsmodels:
```python
pacf_coeffs = list(pacf(x, method="ld", nlags=max_lag))
```
statsmodels `pacf(..., method="ld")` does (source quoted, `statsmodels==0.15.0`):
```python
elif method in ("ld", "lda", "ldadjusted", "ld_adjusted"):
    acv = acovf(x, adjusted=True, fft=False)
    ret = levinson_durbin(acv, nlags=nlags, isacov=True).pacf
```
`acovf(x, adjusted=True, demean=True, fft=False)` (source quoted):
```python
xo = x - x.mean()
acov[0] = xo.dot(xo)
for i in range(lag_len):
    acov[i + 1] = xo[i + 1:].dot(xo[:-(i + 1)])
acov /= n - np.arange(lag_len + 1)   # <-- "adjusted": divide by (n-k), not n
```
`levinson_durbin(sxx_m, nlags, isacov=True)` (source quoted):
```python
phi[1, 1] = sxx_m[1] / sxx_m[0]
sig[1] = sxx_m[0] - phi[1, 1] * sxx_m[1]
for k in range(2, order + 1):
    phi[k, k] = (sxx_m[k] - np.dot(phi[1:k, k-1], sxx_m[1:k][::-1])) / sig[k - 1]
    for j in range(1, k):
        phi[j, k] = phi[j, k-1] - phi[k, k] * phi[k-j, k-1]
    sig[k] = sig[k-1] * (1 - phi[k, k] ** 2)
pacf_[k] = phi[k, k]        # pacf_[0] = 1.0
```
**Rust implementation recipe (no new dependency, per D-06):** compute `acov[0..nlags]` as the mean-demeaned autocovariance with `acov[k] /= (n-k)` (NOT `/n` — this is the "adjusted" estimator, distinct from the biased one used elsewhere), then run the Durbin-Levinson recursion above for k=1..5, returning `phi[k,k]` as `partial_autocorrelation_lag{k}`. The audit's F1 ("lag3..5 = lag-2 formula") is fixed by replacing the ad-hoc Yule-Walker shortcut (`features.rs:506-520`) entirely with this recursion — lag 1 and lag 2 also need re-deriving from the same recursion (their current special-cased values are a *different* estimator, not merely truncated).

### mean_second_derivative_central — FEAT-02 (audit F2)
```python
return (x[-1] - x[-2] - x[1] + x[0]) / (2 * (len(x) - 2)) if len(x) > 2 else np.nan
```
This is the closed-form telescoping sum of the docstring's `Σ ½(x[i+2]-2x[i+1]+x[i])` over `i=1..n-1` — mathematically identical to the current Rust sum-over-windows-of-3 approach, **except the Rust code divides by `(n-2)` only, never introducing the `2×`**. Fix: divide the current result by an additional factor of 2 (`features.rs:154` → `second_deriv / 2.0`). Confirms D-03's "½ factor" exactly.

### last_location_of_maximum / minimum — FEAT-02 (audit F3)
```python
return 1.0 - np.argmax(x[::-1]) / len(x) if len(x) > 0 else np.nan
```
For a 0-based `last_idx`, `argmax(x[::-1]) = n-1-last_idx`, so this formula reduces algebraically to `(last_idx + 1) / n`. Current Rust (`first_last_location_of_value`, `features.rs:678-694`) returns the raw 0-based `last_idx` (divided by `n` at the call site, `features.rs:136,138`) — i.e. `last_idx / n`, missing the `+1`. Fix: add 1 to the last-occurrence index before dividing by `n`. (`first_location_of_maximum`/`minimum` use `argmax(x)/len(x)` — i.e. raw 0-based `idx/n` — which is **already what the Rust code does**; no fix needed there, confirmed by source comparison.)

### time_reversal_asymmetry_statistic — FEAT-02 (audit F4)
```python
one_lag = _roll(x, -lag)          # one_lag[i] == x[i+lag]  (for i in 0..n-2*lag)
two_lag = _roll(x, -2*lag)        # two_lag[i] == x[i+2*lag]
return np.mean((two_lag*two_lag*one_lag - one_lag*x*x)[0:(n-2*lag)])
```
Substituting `i' = i+lag` to align index ranges with the current Rust loop (`for i in lag..n-lag`) gives the target term as:
```
x_lead² · x  −  x · x_lag²
```
The current Rust (`features.rs:898-914`) computes `x_lead.powi(2) * x - x_lag * x.powi(2)` — the second term has `x_lag` and `x` swapped (`x_lag·x²` instead of `x·x_lag²`). Fix is a one-line change: `sum += x_lead.powi(2) * x - x * x_lag.powi(2);`. This is the exact term-order bug D-03/audit-F4 names, now pinned to a literal corrected expression.

### agg_linear_trend — FEAT-02 (audit F7) — ⚠️ parameter mismatch, not just a sign bug
```python
aggregate_result = _aggregate_on_chunks(x, f_agg, chunk_len)   # f_agg in {"max","min","mean","median"}
lin_reg_result = linregress(range(len(aggregate_result)), aggregate_result)
# rvalue = lin_reg_result.rvalue   (scipy linregress; SIGNED Pearson r, not r²)
```
tsfresh's **default** `agg_linear_trend` grid only uses `chunk_len ∈ {5, 10, 50}` and `f_agg ∈ {"max","min","mean","var"}` (confirmed by inspecting `ComprehensiveFCParameters()` this session) — **`chunk_len = n/10` (the project's current data-dependent chunk size) is not in the default grid at all**, and tsfresh's `f_agg="var"` is a chunk-wise variance, not the mean our Rust code always uses. The fixture generator must call `tsfresh.feature_extraction.feature_calculators.agg_linear_trend(x, [{"attr": "rvalue", "chunk_len": N, "f_agg": "mean"}])` directly with our own computed `N = max(len(x)//10, 2)` and `f_agg="mean"` — this is a valid call to the underlying calculator even though it is not one of the names tsfresh would compute by default. Rust fix: make `aggregated_linear_trend`'s r-value signed (`ss_xy.signum() * (ss_xy.powi(2)/(ss_xx*ss_yy)).sqrt()`, or equivalently `ss_xy / (ss_xx.sqrt()*ss_yy.sqrt())`) instead of the current `r_squared.sqrt()` (`features.rs:1049,1074`, always non-negative).

### skewness / kurtosis — FEAT-02 (audit F8, shared with Phase 13 D-05/D-01)
```python
return pd.Series.skew(x, skipna=False)     # pandas adjusted Fisher-Pearson G1
return pd.Series.kurtosis(x)               # pandas adjusted Fisher-Pearson G2 (excess)
```
Identical target to Phase 13's `ts_stats` fix (D-05: `scipy.stats.skew(bias=False)` / `kurtosis(bias=False)` — pandas and scipy's bias-corrected forms are the same G1/G2 estimators). The current `features.rs:67-83` computes the **population** (biased) moment ratio — same category of bug Phase 13 already fixed in `stats.rs`; Phase 14 should reuse the identical corrected formula (`anofox_fcst_core::stats` already has it after Phase 13 — confirm whether it is a `pub` function `features.rs` can call directly, avoiding a second implementation of the same G1/G2 correction).

### fft_coefficient / spectral_centroid / spectral_variance — FEAT-03 (audit F5, F6)
```python
fft = np.fft.rfft(x)                                   # UNNORMALISED one-sided spectrum, length n//2+1
complex_agg(fft[coeff], "real"/"imag"/"abs"/"angle")
```
```python
fft_abs = np.abs(np.fft.rfft(x))
get_centroid(y) = Σ(i · y_i) / Σ(y_i)                   # i = 0..len(y)-1, 1st raw moment
get_variance(y) = get_moment(y,2) - get_centroid(y)**2  # 2nd central moment
```
Both read the **one-sided magnitude spectrum** `|rfft(x)|` (length `n//2+1`), not the full two-sided spectrum including the mirrored negative-frequency half (audit F6's bug: current `spectral_features` at `features.rs:998-1032` runs over the *entire* `fft_coeffs` array, which today is a full-length DFT of size `n`, biasing the centroid toward `n/2`). `np.fft.rfft` is **not** divided by `n` (audit F5's "÷n" bug: current `simple_dft` at `features.rs:978-996` divides by `n as f64`, and it is an O(n²) naive DFT, not O(n log n)).

**Rust recipe avoiding `realfft`:** build a `Vec<Complex<f64>>` of length `n` with `re: values[i], im: 0.0`; run `rustfft::FftPlanner::new().plan_fft_forward(n).process(&mut buf)` (unnormalised forward transform, matching `numpy.fft.fft`'s convention); for a **real** input, `buf[k]` for `k = 0..n/2` is bit-identical to `numpy.fft.rfft(x)[k]` (the redundant negative-frequency half is simply never read). Use only indices `0..=9` for `fft_coefficient_{i}_real/imag/abs` (all 6 reference series have `n ≥ 20`, so `n/2+1 ≥ 11 > 9`, always enough one-sided bins) and the full one-sided slice `buf[0..=n/2]`'s magnitudes for `spectral_centroid`/`spectral_variance`.

### sample_entropy — FEAT-04 (audit F9: 0.981 vs tsfresh's 1.099)
```python
m = 2
tolerance = 0.2 * np.std(x)
xm = _into_subchunks(x, m)              # n-m+1 windows of length m   (NOT n-m)
B = sum(sum(abs(xmi - xm).max(axis=1) <= tolerance) - 1 for xmi in xm)   # full symmetric matrix, self excluded
xmp1 = _into_subchunks(x, m+1)          # n-m windows of length m+1
A = sum(sum(abs(xmi - xmp1).max(axis=1) <= tolerance) - 1 for xmi in xmp1)
return -np.log(A / B)
```
Two distinct bugs in the current Rust (`sample_entropy`/`count_template_matches`, `features.rs:709-764`):
1. **Window count off-by-one:** tsfresh uses `n-m+1` windows for template length `m` (`_into_subchunks` with `num_shifts = (len_x - subchunk_length)//every_n + 1`); the Rust `count_template_matches` loop (`for i in 0..n-m`) only produces `n-m` windows.
2. **Triangular vs full matrix:** tsfresh's nested sum is over the **full `(n-m+1)×(n-m+1)` matrix** (every ordered pair `i,j` including `i==j`, then `-1` to drop the self-match) — i.e. it double-counts every unordered matching pair. The Rust code sums only `j > i` (triangular, no double-count) and additionally normalizes by `(n-m)(n-m-1)/2` (a step tsfresh does not perform at all — `phi_m`/`phi_m1` in tsfresh are *raw, unnormalized* sums, and the ratio `A/B` needs no such normalization since both numerator and denominator window counts cancel differently).
**Fix:** port the Python algorithm literally — `_into_subchunks`-equivalent window generation with `n-m+1`/`n-m` windows, Chebyshev (max-abs) distance, full symmetric double-sum minus self-match, then `-ln(A/B)` directly on the raw sums (no triangular restriction, no combinatorial normalization divisor).

### binned_entropy — FEAT-04 (audit F10)
```python
hist, bin_edges = np.histogram(x, bins=max_bins)   # max_bins = 10 (tsfresh default)
probs = hist / x.size
probs[probs == 0] = 1.0                            # log(1.0)=0, equivalent to skipping empty bins
return -np.sum(probs * np.log(probs))
```
`np.histogram`'s binning is `floor((v-min)/(max-min) * bins)` with the single exception that `v == max` falls into the **last** bin rather than bin `bins` (one past the end) — a floor-based, half-open-interval scheme. Current Rust (`binned_entropy`, `features.rs:642-674`) uses `((v-min)/range * (n_bins-1)).round()` — a **rounding**-based scheme with different bin boundaries, producing different bin populations for any value sitting near a boundary. Fix: replicate `np.histogram`'s floor-based edges exactly (`bin = ((v-min)/range*n_bins).floor().min(n_bins-1)`).

### benford_correlation — FEAT-04 (audit F11, part 1)
```python
x = np.array([int(str(np.format_float_scientific(i))[:1]) for i in np.abs(np.nan_to_num(x))])
benford_distribution = [log10(1+1/n) for n in range(1,10)]
data_distribution = [(x == n).mean() for n in range(1,10)]    # denominator is ALWAYS x.size, incl. zeros/digit-0 entries
return np.corrcoef(benford_distribution, data_distribution)[0, 1]
```
`np.format_float_scientific` normalises **every** nonzero finite value — including magnitudes `< 1` — to a mantissa with a nonzero leading digit (e.g. `0.0034 → "3.4e-03"`, first digit `3`), so values with `|v| < 1` are **not excluded**; they contribute their true leading significant digit. (Only an exact `0` — or a NaN, converted to `0` by `nan_to_num` — produces digit `0`, which simply never matches any of the `1..9` bins, silently lowering every `data_distribution[n]` since the denominator `x.size` is unchanged.) Current Rust (`benford_correlation`, `features.rs:550-603`) explicitly skips any `abs_v < 1.0` (`features.rs:561`) and divides by `total` (the count of digit-producing entries only, not `n`) — both the exclusion and the denominator must be fixed to match tsfresh exactly, confirming D-03/audit-F11's "Benford |v|<1 ignored" with the precise mechanism (scientific-notation leading-digit extraction) and the less-obvious denominator bug.

### permutation_entropy — FEAT-04 (audit F11, part 2)
```python
X = _into_subchunks(x, dimension, tau)       # windows of length `dimension`, stride `tau`
permutations = np.argsort(np.argsort(X))     # rank-encode each window
_, counts = np.unique(permutations, axis=0, return_counts=True)
probs = counts / len(permutations)
return -np.sum(probs * np.log(probs))        # NOT normalised by log(dimension!)
```
tsfresh's default grid uses `tau=1`, `dimension ∈ {3,4,5,6,7}`. The current Rust call `permutation_entropy(values, 3)` already uses `order=3, tau=1 (implicit, contiguous windows)` — a valid default-grid combination — but **normalises** the result by `ln(order!)` (`features.rs:836-843`), a step tsfresh does not perform. Fix: delete the normalization block, return the raw `-Σp·ln(p)`.

### lempel_ziv_complexity — FEAT-04 (audit F11, part 3) — algorithm, not just a formula tweak
```python
bins_edges = np.linspace(np.min(x), np.max(x), bins + 1)[1:]   # quantization edges, e.g. bins=2 -> [midpoint, max]
sequence = np.searchsorted(bins_edges, x, side="left")
sub_strings = set(); ind = 0; inc = 1
while ind + inc <= n:
    sub_str = tuple(sequence[ind:ind+inc])
    if sub_str in sub_strings: inc += 1
    else: sub_strings.add(sub_str); ind += inc; inc = 1
return len(sub_strings) / n
```
This is a different algorithm from the current Rust (`lempel_ziv_complexity`, `features.rs:931-976`), which thresholds at the **mean** (not a `min`/`max`-derived quantization edge) and runs a different dictionary-growth loop (`l += k_max` restart logic) with a `log2(n)/n` normalization that tsfresh does not use at all. tsfresh's default grid is `bins ∈ {2,3,5,10,100}`; **`bins=2` is the closest existing-semantics choice** (binary quantization) but note the threshold itself changes from "mean" to "range midpoint" (`(min+max)/2`) — this is a full rewrite, not a tweak, and is exactly what D-08 ("tsfresh's own Lempel-Ziv algorithm") calls for.

### number_peaks — FEAT-04 (audit F11, part 4)
```python
x_reduced = x[n:-n]
res = (x_reduced > _roll(x, i)[n:-n]) & (x_reduced > _roll(x, -i)[n:-n])  for i in 1..=n  (AND-ed together)
return np.sum(res)
```
tsfresh's default grid is `n ∈ {1,3,5,10,50}` (the "support" — a point must exceed *all* neighbours within `±n`, not just immediate neighbours). The current Rust `count_peaks` (`features.rs:539-548`) is a 3-point local-max filter — algebraically **equal to tsfresh's `number_peaks(x, n=1)`** for interior points (both require `x[i] > x[i-1] ∧ x[i] > x[i+1]`), modulo the boundary handling (tsfresh explicitly excludes the first/last `n` points via slicing; the Rust `.windows(3)` filter implicitly does too, by construction). **Recommendation: verify this numerically in the fixture** (boundary edge cases can still diverge) rather than asserting equality from the algebra alone — this is exactly the kind of claim the D-09 fixture is designed to catch. `number_peaks_threshold_1`/`_2` have no tsfresh counterpart (D-02 applies — direct numpy reference matching the current formula, since nothing in tsfresh's threshold-free `number_peaks` family corresponds to a σ-scaled amplitude threshold).

### NEW FINDING beyond audit F1–F11: `autocorrelation_lag1..10`
```python

sum_product = np.sum((y1 - x_mean) * (y2 - x_mean))
```

The current Rust `autocorr` (`features.rs:481-504`) computes `num/denom` where `denom = Σ_{i=0}^{n-1}(xᵢ-μ)²` (i.e. `n·var(x)`), not `(n-lag)·var(x)`. **Numerically confirmed this session** on a seeded 30-point normal series (`numpy.random.default_rng(42)`):

### Anti-Patterns to Avoid
- **Relying on `tsfresh.extract_features()`'s default settings grid for the fixture:** silently produces the wrong parameter combination (or a missing feature entirely) whenever the chosen param isn't in `ComprehensiveFCParameters()`'s defaults — see the table above. Always call the individual `feature_calculators.<fn>` directly with the exact pinned params.
- **Normalizing/triangularizing `sample_entropy`'s counting the way the current Rust code does:** tsfresh's `A`/`B` are raw symmetric-matrix sums with no combinatorial divisor; adding a normalization (as today's code does) changes the ratio `A/B` because the window counts for `m` and `m+1` differ (`n-m+1` vs `n-m`), so any "normalize, then ratio" approach does not algebraically collapse to tsfresh's "sum raw, then ratio."
- **Assuming `number_peaks` parity by algebra alone:** the 3-point-window vs n-neighbour-support definitions are equal for `n=1` *in the interior*, but boundary slicing differs subtly (`x[n:-n]` vs `.windows(3)`) — verify against the actual fixture rather than skipping the test for this one name.

## Common Pitfalls

### Pitfall 1: Trusting the audit's F1–F11 list as exhaustive
**What goes wrong:** A plan that only fixes the 11 audit-flagged items ships `autocorrelation_lag*` still wrong (the NEW finding above), failing FEAT-05's "all 117 features match or are documented."
**Why it happens:** The audit (`STAT-AUDIT-2026-10-08.md §F`) was a sampling pass, not exhaustive; `features.rs` was never run against the installed tsfresh this session until now.
**How to avoid:** The 117-row mapping file (D-01) is the actual completeness gate, not the audit list — every name needs its own row and its own fixture assertion, independent of whether the audit named it.
**Warning signs:** A plan task list with exactly 11 fix items and no "verify the remaining ~106 names against the fixture" task.

### Pitfall 2: Fixture generator using the convenience `extract_features()` API
**What goes wrong:** Silent parameter mismatch for `agg_linear_trend`, `approximate_entropy`, or any feature whose exact param isn't in `ComprehensiveFCParameters()`'s defaults — the fixture then encodes the *wrong* tsfresh value, and the Rust parity test "passes" against a wrong target.
**Why it happens:** `extract_features()` looks like the natural entry point; its default grid looks comprehensive until you dump it (as done this session) and compare row-by-row.
**How to avoid:** Call `feature_calculators.<fn>` directly, always, with the project's exact parameter values as the mapping file states them.
**Warning signs:** A generator script that imports `ComprehensiveFCParameters` or calls `tsfresh.extract_features(...)` instead of individual calculator functions.

### Pitfall 3: `sample_entropy`'s window-count and double-counting bugs compounding
**What goes wrong:** Fixing only the normalization (dropping the triangular divisor) without also fixing the `n-m` vs `n-m+1` window-count off-by-one still produces a wrong value — both bugs must be fixed together, since they interact multiplicatively through the ratio `A/B`.
**Why it happens:** The two bugs look independent but both shift the effective window count, and fixing one in isolation can look "closer" to 1.099 without actually being correct.
**How to avoid:** Port `_into_subchunks`'s window-count formula (`n - subchunk_length + 1`) and the full symmetric-matrix double-sum together, verify against the fixture's literal 1.099 value (quoted in CONTEXT.md's Specific Ideas), not just "closer than before."

### Pitfall 4: WASM build silently breaking from the new direct `rustfft` dependency
**What goes wrong:** `rustfft` is unconditionally required by `fdars-core` today (not feature-gated), so it's already compiled for WASM — but promoting it to a *direct* `anofox-fcst-core` dependency changes the Cargo dependency graph's resolution path, and a version mismatch between the direct pin and the transitive one could, in principle, create a duplicate-crate build error.
**Why it happens:** Cargo feature unification quirks when the same crate appears both as a direct dep and transitively via a different path.
**How to avoid:** Pin the exact same version already in `Cargo.lock` (`6.4.1`, `default-features = false` to match what `fdars-core` already pulls), then run the WASM build check named in CONTEXT.md's DoD (`.planning` Specific Ideas section) before considering FEAT-03 done.

## Code Examples

### PACF Durbin-Levinson recursion (target algorithm, Rust pseudocode)
```rust
// Source: derived from statsmodels==0.15.0 acovf()+levinson_durbin() source, quoted above
fn pacf_durbin_levinson(values: &[f64], max_lag: usize) -> Vec<f64> {
    let n = values.len();
    let mean = values.iter().sum::<f64>() / n as f64;
    let xo: Vec<f64> = values.iter().map(|v| v - mean).collect();
    // "adjusted" autocovariance: divide by (n-k), not n
    let mut acov = vec![0.0; max_lag + 1];
    acov[0] = xo.iter().map(|v| v * v).sum::<f64>() / n as f64;
    for k in 1..=max_lag {
        let s: f64 = (k..n).map(|i| xo[i] * xo[i - k]).sum();
        acov[k] = s / (n - k) as f64;
    }
    // Durbin-Levinson recursion
    let mut phi = vec![vec![0.0; max_lag + 1]; max_lag + 1];
    let mut sig = vec![0.0; max_lag + 1];
    phi[1][1] = acov[1] / acov[0];
    sig[1] = acov[0] - phi[1][1] * acov[1];
    let mut pacf = vec![0.0; max_lag + 1];
    pacf[0] = 1.0;
    pacf[1] = phi[1][1];
    for k in 2..=max_lag {
        let dot: f64 = (1..k).map(|j| phi[j][k - 1] * acov[k - j]).sum();
        phi[k][k] = (acov[k] - dot) / sig[k - 1];
        for j in 1..k {
            phi[j][k] = phi[j][k - 1] - phi[k][k] * phi[k - j][k - 1];
        }
        sig[k] = sig[k - 1] * (1.0 - phi[k][k].powi(2));
        pacf[k] = phi[k][k];
    }
    pacf
}
```

### FFT via rustfft reproducing numpy.fft.rfft's one-sided bins
```rust
// Source: rustfft 6.4.1 API (training knowledge of the crate's public interface — [ASSUMED],

use rustfft::{FftPlanner, num_complex::Complex};
fn one_sided_spectrum(values: &[f64]) -> Vec<Complex<f64>> {
    let n = values.len();
    let mut buf: Vec<Complex<f64>> = values.iter().map(|&v| Complex { re: v, im: 0.0 }).collect();

    buf
}
```

## Open Questions

1. **Does `zero_crossing_rate` get a documented "no tsfresh equivalent" entry, or does it get redefined to match `number_crossing_m(m=0)`?**
   - What we know: tsfresh's only crossing calculator (`number_crossing_m`) returns a raw count at an arbitrary threshold `m`, not a rate over `n-1` with exact-zero exclusion; `m=0` is in its default grid.
   - What's unclear: whether the user wants `zero_crossing_rate` kept as its current custom rate formula (D-02, numpy reference) or redefined to be `number_crossing_m(m=0)/(n-1)` for closer conceptual alignment with tsfresh (still not an exact tsfresh value, since tsfresh never divides by `n-1`).
   - Recommendation: keep the current formula, tagged `reference: numpy/scipy` in the mapping (D-02's explicit category) — this needs no behaviour change, only a mapping-file entry and a doc note that no tsfresh calculator corresponds to a normalized crossing rate.

2. **Does the project want `number_peaks`'s boundary semantics pinned bit-for-bit against tsfresh's exact slicing (`x[n:-n]`), or is "matches on the 6 reference series" sufficient?**
   - What we know: the two definitions agree in the interior; boundary behaviour for `n=1` (first/last element) has not been algebraically proven equal, only asserted likely-equal.
   - What's unclear: whether any of the 6 reference series (or the constant-series edge case) actually exercises the boundary disagreement, if one exists.
   - Recommendation: let the fixture decide — if `number_peaks` matches on all 6+1 series within tolerance, treat it as confirmed-correct (no Rust change needed, same bucket as `cid_ce`/`c3_lag*`); if it doesn't match, the fixture's failure message will show exactly which series/index diverges.
