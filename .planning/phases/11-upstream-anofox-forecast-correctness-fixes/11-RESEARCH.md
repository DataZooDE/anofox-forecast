## Summary

The upstream `anofox-forecast` crate (origin/main `c57e4fa`, crate version 0.15.10) has five independent, well-localized statistical defects that the extension's audit (`STAT-AUDIT-2026-10-08.md` §C, §H) already pinpointed from black-box comparison with R/statsmodels; this research confirms every defect by reading the actual source and narrows each to specific functions and line ranges, which materially shrinks the fix surface the planner needs to scope:

1. **ADF/KPSS (`src/validation/stationarity.rs`, 800 lines, single file)** — `adf_test`'s regression (`compute_adf_statistic`, lines 190-237) never includes lagged Δy terms despite a lag being "selected" (`select_lag_aic`) and a comment describing the augmented form; the lag only trims the sample. `adf_p_value` (lines 240-263) is a 9-point hand-built table, not MacKinnon's response surface. `kpss_p_value` (lines 266-281) is close but not clamped to statsmodels/tseries' documented [0.01, 0.10] range. Public signatures (`adf_test(series, Option<usize>)`, `kpss_test(series, Option<usize>)`) must stay source-compatible (the extension's `anofox-fcst-core/src/validation.rs` wraps the exact `StationarityResult` field layout).

2. **AutoARIMA (`src/models/arima/auto_arima.rs`, `diff.rs`, `model.rs`)** — three separate smaller bugs, not one: (a) `d` is chosen by a crude variance-ratio heuristic (`diff.rs:284-306`), not KPSS; (b) seasonal-pattern detection (`auto_arima.rs:199-211`, STL seasonal-strength >0.64 — already R-correct) and `D`-selection (`auto_arima.rs:215-240`, a *different*, ad hoc variance-ratio test) are inconsistent with each other; (c) the AICc candidate-scoring function (`model.rs::score_order`, two independently-maintained copies for plain ARIMA at lines 325-481 and SARIMA at lines 2232-2378) computes effective sample size inconsistently across model orders in the plain-ARIMA copy, and omits the AICc finite-sample correction entirely in the SARIMA copy. Each sub-bug is independently fixable and none requires touching the ADF/KPSS branch — critically, **the KPSS-based `d` selection R's `ndiffs` needs can be implemented by comparing the KPSS *statistic* directly against the already-correct `critical_values.cv_5pct` (confirmed correct by the audit), avoiding any dependency on branch (a)'s p-value fix.**

3. **ETS (`src/models/exponential/ets.rs`)** — the multiplicative-error log-likelihood term sums `ln|y|` instead of `ln|ŷ|` at two call sites inside a shared macro (`ets_likelihood_loop!`, invoked at lines 390 and 416); seasonal models skip the first `period` observations from the likelihood sum (`start_idx = period`, line 792); every smoothing parameter is bounded independently to `[0.0001, 0.9999]` with no α/β/γ coupling (bounds arrays at lines 1081-1083, 1220-1224, 1334-1339, 1457-1464, etc.). The AutoETS candidate generator (`auto_ets.rs`) already excludes multiplicative-trend models structurally (no such `TrendType` variant exists) and already excludes the M,A,A / M,Ad,A "unstable" combination R excludes (`auto_ets.rs:283-289`) — **the candidate-set part of UPST-02 needs no code change**, only the likelihood/constraint fix.

4. **Theta (`src/models/theta/model.rs`)** — the default `Theta::new()` (Standard Theta Model) hard-codes `alpha: Some(0.1), optimize: false` (lines 91-96) "to match statsforecast STM," which is exactly the random-walk-biased behavior the audit flagged against R's `thetaf` (which always optimizes α). The crate *already has* a correct SES-optimizing α estimator (`optimize_alpha`, lines 514-529, Nelder-Mead SSE minimization) used by the `optimized()` constructor, and the forecast formula (Fiorucci et al. 2016 state-space form, lines 647-648) is already algebraically equivalent to thetaf's `level + drift·(h + …)` at θ=2. **The fix is narrower than the audit framing suggests: make STM's default behavior use the existing optimizer**, not write a new one.

5. **TBATS/MSTL/GARCH intervals** — three unrelated, shallow ad hoc interval formulas: TBATS uses `√(h+1)` (pure random-walk growth, ignoring its own seasonal state), MSTL uses an arbitrary `√(1+0.1h)`, and GARCH's `predict_with_intervals` calls a `forecast_variance` recursion (lines 454-516) that is *structurally* a textbook GARCH(p,q) multi-step variance forecast — meaning the audit's reported 0.13× undersizing is probably a parameter-estimation (likelihood/optimizer) bug, not an interval-formula bug, and needs a short diagnostic spike before deciding fix-vs-NULL per D-10.

**Primary recommendation:** Plan Phase 11 as five independently-plannable, independently-mergeable work units matching the five PR branches in D-01 (ADF/KPSS; AutoARIMA; ETS; Theta; TBATS/MSTL/GARCH), each with its own R/Python fixture-generation step and its own `cargo test` + `cargo fmt --check` + `cargo clippy` gate, executed inside `~/projects/rust/anofox-forecast` against branches cut from `origin/main` (`c57e4fa`). Sequence (c) ETS before (d) Theta is *not* required (no shared helper found — see Architecture Patterns), contrary to CONTEXT.md's cautious phrasing; no branch pair in this phase has a genuine code dependency once AutoARIMA's `d`-selection is implemented against `critical_values` rather than `p_value`.

### Pattern 1: MacKinnon (2010) response-surface p-values
**What:** statsmodels' `adfuller`/`coint` do not use a static table; they fit the test statistic through a response-surface regression `τ(n) = β∞ + β1/n + β2/n² + β3/n³` with case-specific (`"n"`/`"c"`/`"ct"`) coefficients published in MacKinnon (2010), then look up/interpolate the resulting asymptotic critical value distribution to produce a p-value (`mackinnonp`) or exact critical values at a given significance level (`mackinnoncrit`).
**When to use:** Replace the entire `adf_p_value` 9-point table (`stationarity.rs:240-263`) and the fixed three `CriticalValues` constants (`stationarity.rs:85-89`, currently hard-coded to the "c" case only) with per-regression-type (n/c/ct) tables and the response-surface formula.
**Example (statsmodels' documented algorithm, not verbatim source — statsmodels' own source is GPL-compatible but not reproduced here):**
```
# For regression type "c" (constant only), N=1:
```

### Pattern 3: KPSS-based `d` selection without depending on branch (a)
**What:** R's `forecast::ndiffs(x, test="kpss", alpha=0.05)` repeatedly KPSS-tests the (progressively differenced) series and increments `d` while the null of stationarity is rejected, up to `max.d`. Rejection at level α is equivalent to `statistic > critical_value(α)` — it does **not** require a correct p-value, only a correct critical-value table.
**When to use:** AutoARIMA's `d`-selection fix (D-06, branch b). This crate's `kpss_test` already returns `critical_values.cv_5pct` correctly (confirmed by the audit: "statistic itself correct"; the `CriticalValues` struct's three constants at `stationarity.rs:325-329` — `cv_1pct: 0.739, cv_5pct: 0.463, cv_10pct: 0.347` — match `tseries::kpss.test`'s published table exactly).
**Example:**
```rust
// AutoARIMA d-selection (target), avoiding any dependency on branch (a)'s p-value fix:
fn ndiffs_kpss(values: &[f64], alpha: f64, max_d: usize) -> usize {
    let mut d = 0;
    let mut series = values.to_vec();
    while d < max_d {
        let result = crate::validation::kpss_test(&series, None);
        let cv = match alpha {
            a if a <= 0.01 => result.critical_values.cv_1pct,
            a if a <= 0.05 => result.critical_values.cv_5pct,
            _ => result.critical_values.cv_10pct,
        };
        if result.statistic > cv {
            d += 1;
            series = crate::models::arima::diff::difference(&series, 1);
        } else {
            break;
        }
    }
    d
}
```
This is this session's own derivation from R's documented `ndiffs` algorithm [CITED: https://pkg.robjhyndman.com/forecast/reference/auto.arima.html describes `test="kpss"` as the default unit-root test fed to `ndiffs()`] combined with the crate's own already-correct critical-value constants [VERIFIED: src/validation/stationarity.rs:325-329 — `cv_1pct: 0.739, cv_5pct: 0.463, cv_10pct: 0.347`] — not copied from any single source; the planner should treat the loop structure as a recommendation, not a verified-against-R-source snippet.

### Pattern 5: Fix AICc sample-size consistency (not a formula rewrite)

### Pattern 6: ETS likelihood — fix site and scope
**What:** The shared macro `ets_likelihood_loop!` (`ets.rs:372-423`) accumulates `_sum_log += $y.abs().ln()` inside both the `nonseasonal` (line 390) and `seasonal` (line 416) macro arms, for every model whose error type is multiplicative (`$is_mult_error`). **When to use:** D-07. Fix both macro-arm occurrences in one place (the macro itself), which propagates to every model that invokes it (lines 836-936 show 9 invocation sites across ANN/MNN/AAN-family/seasonal variants) — a single-point fix, not 9 separate ones.

### Pattern 7: ETS "usual constraints" — where bounds are set
**What:** Every `optimize_params` branch builds its own flat `bounds: Vec<(f64,f64)>` with each of α/β/γ/φ independently clamped to `[0.0001, 0.9999]` (or `[0.8, 0.98]` for φ) — e.g. `ets.rs:1081-1083` for the (α,β) trend-only case, `:1220-1224` and `:1333-1339` for the seasonal joint-optimization cases, `:1457-1464` for the damped-seasonal case. R's `ets()` (and the standard admissibility region) requires the *coupled* constraints `0 < β < α` and `0 < γ < 1 − α` (not independent boxes) to keep the state-space model's transition matrix eigenvalues inside the unit circle for the "usual" (non-"admissible-region") parameter space.
**When to use:** D-07. This requires changing the *objective/bounds-handling*, not just the bounds array literal — the in-house `nelder_mead`/`lbfgs_optimize` (`src/utils/optimization.rs`) take simple box bounds, so enforcing `β<α`/`γ<1−α` needs either a reparameterization (e.g., optimize `β' = β/α ∈ (0,1)` and recover `β=β'·α`) or a penalty term in the objective. This is a genuine design decision left to "Claude's Discretion" per CONTEXT.md.
[VERIFIED: src/models/exponential/ets.rs:1081-1083 (`(0.0001, 0.9999), (0.0001, 0.9999), level_bounds, trend_bounds`), :1220-1224 (`joint_bounds.push((0.0001, 0.9999)); joint_bounds.push((0.0001, 0.9999)); joint_bounds.push(level_bounds); joint_bounds.extend_from_slice(&seasonal_bounds);`) — both show independent box bounds with no coupling term]

### Pattern 8: Hyndman et al. (2008) analytic interval variances — exact formulas, and why "class 2" doesn't apply here
**What:** fpp3 (the open textbook companion to the `forecast` package, by the same author as the 2008 book) Table 8.8 gives the exact closed-form h-step forecast variance `σ²_h` for the 6 additive-error models that have no multiplicative trend or where trend/season combination admits a closed form:

| Model | σ²_h formula |
|---|---|
| (A,N,N) | `σ²[1 + α²(h−1)]` |
| (A,A,N) | `σ²[1 + (h−1){α² + αβh + (1/6)β²h(2h−1)}]` |
| (A,Aḏ,N) | (damped variant; involves φ, more complex — see source) |
| (A,N,A) | `σ²[1 + α²(h−1) + γk(2α+γ)]`, k = ⌊(h−1)/m⌋ |
| (A,A,A) | `σ²[1 + (h−1){α² + αβh + (1/6)β²h(2h−1)} + γk{2α + γ + βm(k+1)}]` |
| (A,Aḏ,A) | (damped + seasonal; more complex — see source) |

For multiplicative-*error* models, "there are no known formulas for prediction intervals" in general — the `forecast` package uses "simulated future sample paths and computes prediction intervals from the percentiles."
[CITED: https://otexts.com/fpp3/ets-forecasting.html §8.7, Table 8.8, fetched this session]

**Key scoping finding for this crate specifically:** this crate's `TrendType` enum (used throughout `ets.rs`/`auto_ets.rs`) has only `{None, Additive, AdditiveDamped}` — there is **no multiplicative-trend variant**. Hyndman's "class 2" models (those needing more complex recursive-but-still-closed-form variances) arise specifically from multiplicative-trend combinations, which this crate cannot construct. **Therefore every additive-error model this crate can produce is already in Hyndman's "class 1"** (the 6-row table above covers it completely), and UPST-03's simulation path is needed *only* for multiplicative-*error* models (any `ErrorType::Multiplicative` spec), regardless of trend/season type. This narrows D-08's scope: implement the 6 closed-form variances for additive-error models, route every multiplicative-error model to simulation — no "class 2" branch needs to be written.
[VERIFIED: the crate's `TrendType` has no multiplicative variant — confirmed via `auto_ets.rs:251-259`, quoted in Pattern-adjacent finding in Summary §3 above: `let trend_types = if self.config.allow_damped { vec![TrendType::None, TrendType::Additive, TrendType::AdditiveDamped] } else { vec![TrendType::None, TrendType::Additive] };` — no `TrendType::Multiplicative` arm exists in the enum at all (grep across `auto_ets.rs` and `ets.rs` found zero references)]

### Pattern 9: Theta STM — the real fix is a default flag, not new math
**What:** `Theta::new()` (`model.rs:91-96`) sets `alpha: Some(0.1)`, `optimize: false` — a deliberate design choice documented as "matching statsforecast STM." `Theta::optimized()` (`model.rs:213-220`) sets `optimize: true` and, when `fit()` runs with `self.optimize && !self.skip_optimization` true (`model.rs:799-802`), calls `Self::optimize_alpha(&deseasonalized)` (`model.rs:514-529`) — a Nelder-Mead SSE minimizer over `[0.0001, 0.9999]` that is methodologically identical to what R's `thetaf` does ("Alpha is estimated by fitting an SES model to the data" [CITED: https://github.com/robjhyndman/forecast/blob/master/R/theta.R, via WebSearch summary this session]).
**When to use:** D-09. The forecast formula itself (`predict_internal`, `model.rs:647-648`: `smoothed + (1.0 - 1.0 / self.theta) * b * (1.0 / alpha + (h as f64 - 1.0))`) is the Fiorucci et al. (2016) state-space form; at `theta=2.0` (STM's fixed value) this is algebraically `smoothed + 0.5*b*(1/alpha + h - 1)`, matching thetaf's documented `drift = slope/2` scaling. **No formula rewrite needed** — only flip the default `Theta::new()` to behave like `optimized()` (or merge the two constructors), and update the doc comments (`model.rs:91`, `theta/auto.rs:17,53`, `theta/dynamic.rs:83`) that describe "fixed alpha=0.1" as intentional.

### Anti-Patterns to Avoid
- **Fixing AutoARIMA's `d` selection by calling the (still-buggy-until-merged) `p_value` field:** creates a real cross-branch dependency between (a) and (b) that CONTEXT.md's D-01 explicitly wants avoided. Use the critical-value comparison (Pattern 3) instead.
- **Rewriting GARCH's interval formula before diagnosing the likelihood/optimizer:** the variance *recursion* (`garch.rs:454-516`) is structurally correct; changing the interval-width formula without first checking whether `omega`/`alpha`/`beta` themselves are mis-estimated risks fixing the wrong layer and leaves the audit's 0.13× gap unexplained.
- **Treating the Theta fix as requiring new interval math:** the existing `predict_with_intervals` growth-factor formula (`model.rs:969-983`, standard SES variance-growth) is already structurally the right family of formula; conflating "fix α estimation" with "fix interval formula" risks unnecessary rewrites on branch (d).
- **Duplicating the STL seasonal-strength computation a third time:** AutoARIMA already has it twice (correctly in `has_seasonal_pattern`, incorrectly reinvented in `suggest_seasonal_differencing`) — unify to one call site (Pattern 4), don't add a third variant for e.g. a future `nsdiffs`-shaped public API.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| ADF/KPSS asymptotic p-values | A new hand-fit table (what the current code already is) | MacKinnon (2010) response-surface coefficients, reproduced from statsmodels' `adfvalues.py` tables (with the documented 5-coefficient caveat) or directly from the MacKinnon (2010) working paper | These are the de facto standard tables every stats package (R `urca`, Python `statsmodels`) already ships; re-deriving them from simulation would be a multi-day Monte-Carlo undertaking the audit never asked for |
| GARCH/ETS/ARIMA numerical optimization | A new optimizer crate or hand-rolled gradient descent | The crate's existing `nelder_mead`/`lbfgs_optimize` (`src/utils/optimization.rs`), already used by every affected model | Adding a dependency here would touch `Cargo.toml` across potentially all 5 branches — exactly the cross-branch coupling D-01 wants avoided |
| KPSS/ADF critical value tables | New simulated critical values | The crate's existing `CriticalValues` struct and its already-audit-confirmed-correct KPSS constants (`stationarity.rs:325-329`) | Already correct; only the ADF constants (currently hard-coded to the "c"/constant case regardless of regression type, `stationarity.rs:85-89`) need extending to "n"/"ct" variants, not re-deriving from scratch |

**Key insight:** every one of the five defect areas has an *existing, mostly-correct* piece of machinery nearby in the same file (a correct KPSS statistic next to a broken p-value; a correct STL seasonal-strength test next to a broken ad hoc one; a correct SES optimizer next to a hard-coded fixed α; a correct AICc formula in one file next to a missing one in its sibling file). The fastest, lowest-risk path for every branch in this phase is "reuse/extend the sibling that's already right," not "write new statistical machinery."

## Common Pitfalls

### Pitfall 1: Confusing "the statistic is right" with "nothing is wrong" in validation.rs
**What goes wrong:** The audit (and this research) separately confirms the ADF *t-statistic formula* in `compute_adf_statistic` would be fine *if* the regression were actually augmented — but because the regression never includes lagged Δy terms, changing only the p-value function (without fixing the regression) will produce a "correctly computed p-value for the wrong statistic."
**Why it happens:** The two bugs (missing augmentation, wrong p-value table) live in adjacent functions and are easy to fix independently without re-testing the combination.
**How to avoid:** D-04's fixture tests must assert the *statistic* against `urca::ur.df`/`adfuller` first, independently of the p-value, before trusting any p-value fixture.
**Warning signs:** A fixture test that only checks `p_value` ranges (like the existing `adf_p_value_boundaries` test at `stationarity.rs:759-775`, which only checks `p1 < 0.01` etc.) rather than exact statistic values — this is exactly the "length-only" testing debt the project's `.planning/REQUIREMENTS.md` TEST-01/TEST-02 calls out.

### Pitfall 2: AICc comparability requires fixing BOTH the `(0,0)` branch AND the SARIMA AICc term, in the same PR
**What goes wrong:** Fixing only the sample-size inconsistency in plain `ARIMA::score_order` (Pattern 5, fix 1) without also adding the AICc correction to `SARIMA::score_order` (Pattern 5, fix 2) leaves seasonal model selection using plain AIC (not AICc), which the Hyndman-Khandakar algorithm (D-06) explicitly requires be AICc for small/moderate samples.
**Why it happens:** These are two separate, independently-discoverable bugs in two separate functions that happen to serve the same `AutoARIMA::fit` call — easy to fix one and ship, believing "AICc is done."
**How to avoid:** Write one Monte-Carlo test (per D-03) exercising *both* seasonal and non-seasonal candidate grids in the same run; the random-walk/AR(0.7) selection-frequency targets in CONTEXT.md's Specific Ideas section implicitly require both.
**Warning signs:** A fix that only touches `model.rs:325-481` (non-seasonal) and doesn't touch `:2232-2378` (seasonal) is incomplete for any series with a seasonal period configured.

### Pitfall 3: ETS likelihood fix inside a macro affects every model variant simultaneously
**What goes wrong:** Because `ets_likelihood_loop!` is invoked at 9+ call sites (`ets.rs:836-936`) covering every (error × trend × seasonal) combination, a naive "fix one call site" patch leaves the other 8 broken, while a correct macro-body fix (Pattern 6) silently changes log-likelihood values for *every* model including ones the audit didn't flag as visibly wrong (because additive-error models are unaffected — `$is_mult_error` gates the buggy line).
**Why it happens:** Macro-based code deduplication hides the fan-out from a casual `grep` for the symptom (AirPassengers MAM mismatch) back to the actual bug location.
**How to avoid:** Fix the macro body once; re-run fixture tests for *every* model variant that sets `is_mult_error = true`, not just the one the audit's example (AirPassengers MAM) used.
**Warning signs:** A diff that touches 9 call sites individually instead of the 2-line macro body is a sign the fix was applied in the wrong place (or a sign the macro itself needs restructuring, which is a valid but larger alternative).

### Pitfall 4: Fixing Theta's default without checking `AutoTheta`/`DynamicTheta`/`OptimizedTheta` doc comments
**What goes wrong:** `theta/auto.rs:17,53` and `theta/dynamic.rs:83` independently describe "STM — fixed alpha=0.1" as a *feature* of the overall Theta family's design (AutoTheta tries STM/OTM/DSTM/DOTM as 4 distinct candidates). Flipping `Theta::new()`'s default changes what "STM" *means* throughout the family without those doc comments being updated, and — more importantly — may collapse AutoTheta's 4-way candidate diversity into fewer distinct candidates if STM and OTM now behave identically.
**Why it happens:** The fix is architecturally simple (one struct literal) but semantically ripples through a family of 4+ model variants that reference "STM" as a specific, documented behavior.
**How to avoid:** Check whether `AutoTheta`'s candidate generation (`theta/auto.rs`) constructs its own `Theta` instances independently of `Theta::new()`'s default (i.e., does it explicitly set `alpha`/`optimize` per candidate, or does it rely on the default?) before assuming the fix is a one-line change; if AutoTheta explicitly sets STM's fixed-α, the one-line default flip in `Theta::new()` may not even reach AutoTheta's STM candidate, in which case **both** sites need the fix.
**Warning signs:** `AutoTheta`'s candidate list after the fix still contains two behaviorally-identical "STM" and "OTM" candidates (both now optimize α) — a sign the fix needs to differentiate the family's remaining 3 candidates (e.g., DSTM = dynamic + fixed, DOTM = dynamic + optimized) rather than collapsing all 4 toward "optimized."

### Pitfall 5: TBATS/MSTL interval fixes risk hiding a GARCH diagnosis gap behind D-10's NULL-interval escape hatch
**What goes wrong:** Branch (e) covers three unrelated models in one PR (per D-01's grouping). It would be easy to "fix" TBATS and MSTL (shallow ad hoc formulas, Pattern-level fixes) and then declare GARCH "intractable, return NULL intervals" under D-10 without first running the short diagnostic spike this research recommends (checking whether `omega`/`alpha`/`beta` estimates themselves match `arch`/statsforecast, independent of the interval formula) — potentially discarding working interval machinery over a parameter-estimation bug that's actually fixable.
**Why it happens:** D-10 explicitly permits "return NULL" as a valid outcome, which is the path of least resistance once the PR deadline for branch (e) approaches.
**How to avoid:** The plan for branch (e) should include an explicit "diagnose GARCH parameter estimates against a reference (Python `arch` package or hand-derived closed-form on simulated data) BEFORE deciding fix-vs-NULL" task, not a "fix intervals, else NULL" task.
**Warning signs:** A GARCH PR description that says "intervals too narrow, returning NULL" without a sentence explaining *why* the variance recursion (which this research found structurally correct) produces narrow results.

## Open Questions

1. **Does `AutoTheta`'s candidate generation construct `Theta` instances independently of `Theta::new()`'s default, or rely on it?**
   - What we know: `theta/auto.rs:17,53` document "STM — fixed alpha=0.1" as one of AutoTheta's named candidates; `Theta::new()` is the struct that currently hard-codes that behavior.
   - What's unclear: Whether `auto.rs`'s candidate-construction code calls `Theta::new()` directly (in which case fixing the default auto-propagates) or constructs a `Theta` with explicit `alpha`/`optimize` fields bypassing the default (in which case `auto.rs` needs its own edit too).
   - Recommendation: Grep `theta/auto.rs` for its `Theta` construction call sites as the first task of branch (d)'s plan, before committing to "one-line fix."

2. **What is the actual root cause of GARCH's 0.13× interval width (parameter estimation vs. formula vs. something else)?**
   - What we know: the variance-forecast recursion (`garch.rs:454-516`) is structurally a standard GARCH(p,q) multi-step forecast; `predict_with_intervals` (`:703-722`) correctly calls it and applies a standard `z*se` interval.
   - What's unclear: whether the `omega`/`alpha`/`beta` parameter *estimates* from `fit()` (not read in depth this session — `garch.rs:526` onward) match a reference implementation; a subtly wrong likelihood or constraint during estimation would produce correctly-formed-but-wrong-width intervals exactly matching the audit's symptom.
   - Recommendation: branch (e)'s plan should budget a short (half-day) diagnostic task — fit the crate's GARCH on one of the `validation/data/` series, compare `omega`/`alpha`/`beta` against Python `arch` (needs `uv add arch` to `validation/pyproject.toml` first) — before writing any interval-formula code.

3. **Does statsmodels' documented 5-coefficient transcription discrepancy from the MacKinnon (2010) paper (statsmodels GitHub issue #10271) matter for this phase's fixture-matching goal?**
   - What we know: D-04 asks the crate to match statsmodels' `adfuller`/`mackinnonp` *behavior* on fixtures, and separately to match `urca::ur.df`. If `urca` uses the paper's original coefficients and statsmodels uses its own (slightly different) transcription, the two reference implementations could disagree with each other at the margin.
   - What's unclear: whether any of this phase's planned fixture series actually fall into the specific `(N, significance-level)` cells where the 5 documented discrepancies occur (the issue cites `N=2` cases; this crate's univariate ADF is always `N=1`, which the GitHub issue summary did not confirm is unaffected).
   - Recommendation: generate fixtures from *both* `urca::ur.df` (R) and `statsmodels.tsa.adfuller` (Python) for the same series and confirm they agree before trusting either as sole ground truth; if they disagree, document which one the crate's implementation follows and why.

4. **Is the crate's upstream CI's floating `stable` Rust toolchain ("Rust 1.98 clippy" per CONTEXT.md) still `1.98` by the time this phase executes?**
   - What we know: `.github/workflows/ci.yml` pins `dtolnay/rust-toolchain@stable` for the `clippy`/`fmt`/`docs`/`audit`/`deny` jobs and a `[stable, beta, nightly]` matrix for `test` — there is no hard version pin in the repo; "1.98" is whatever `stable` resolves to at CI run time.
   - What's unclear: whether any of the five branches' fixes need a clippy lint allowance that differs between whatever `stable` was at research time vs. execution time.
   - Recommendation: run `cargo clippy --all-features -- -D warnings` locally against current `stable` as a smoke test early in each branch's plan, rather than assuming parity with the "1.98" figure cited in CONTEXT.md's code_context section.
