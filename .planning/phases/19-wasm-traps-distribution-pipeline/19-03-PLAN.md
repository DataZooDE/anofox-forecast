<objective>
Fix BUG-02 (#289): `ts_features_list()` and `ts_features_config_template()` trap in DuckDB-Wasm with `memory access out of bounds`. Per the locked CONTEXT #289 decision 2, reproduce first in the Node DuckDB-Wasm harness, find the root cause, then fix it; per decision 3, done means 117 rows natively AND in DuckDB-Wasm (wasm_eh), the instance stays usable for the next statement, and both functions are in the CI-gated curated WASM subset.

Planner root-cause finding (verified by reading source, to be confirmed empirically by the repro): `crates/anofox-fcst-ffi/src/lib.rs` lines 46-99 define, for `target_family = "wasm"` only, a size-prefixed `malloc`/`free` shim over `std::alloc` that returns `base + size_of::<usize>()`. `anofox_ts_features_list` (lib.rs ~3578) allocates the name array and every name with that shim, but `src/table_functions/ts_features.cpp` releases them with libc `free()` (lines 71, 73, 160, 162) — on wasm32 that frees a pointer 4 bytes past the real allocation and corrupts the emscripten heap. Natively the shim is libc `malloc`, which is why native never fails. These are the only raw `free()` calls in `src/`. This matches RESEARCH Pitfall 3 candidate (b) (allocator mismatch) and explains why the 9 DATAZOO_GUARD-wrapped functions in anofox-statistics are unaffected.

Second defect found during planning (same functions, same file): the row cursor and the name vector live in bind data that Execute mutates, so `PREPARE p AS SELECT count(*) FROM ts_features_list(); EXECUTE p; EXECUTE p;` returns 117 then 0 on the native v2.0.0 build. That violates "return 117 rows"; it is fixed here by moving per-execution state into a GlobalTableFunctionState.

Output: paired FFI free function with a Rust test, fixed C++ catalog functions, exact-count sqllogictests, corrected WASM skip list, curated gate entry, CHANGELOG entry.
</objective>
