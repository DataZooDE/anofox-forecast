> **AMENDMENT (2026-10-23, from 20-02 execution, overrides every recipe below):** do NOT use `WITH _ts_src AS MATERIALIZED (...)`. On DuckDB v2.0.0 it intermittently raises `INTERNAL Error: Pipeline broadcast exchange received invalid producer batch index` (12/30 runs). Use the recipe proven in 20-02 instead: pass the native `(SELECT * FROM _ts_passthrough(source) ORDER BY ALL)` as its source (40/40 clean, cheaper), together with the shared `src/include/ts_collect_finalize.hpp` barrier. Every acceptance check of the form `contains "AS MATERIALIZED"` is replaced by `contains "_ts_passthrough(" and "ORDER BY ALL"`. See 20-02-SUMMARY.md and deferred-items.md. API rule (Phase 20.1): public macro signatures and output columns must stay identical (check DESCRIBE before and after).

## Planner-verified facts (2026-10-23, build/release at 9d11361, DuckDB v2.0.0, 20 cores)

- Forecast path: `ts_forecast_by` is `SELECT group_col, ... FROM (SELECT group_col, unnest(_ts_forecast_scalar(LIST(date_col ORDER BY date_col), LIST(target_col::DOUBLE ORDER BY date_col), ...), recursive := true) FROM query_table(source::VARCHAR) GROUP BY group_col)`: a hash aggregate (a sink that combines across pipelines) plus a scalar, so it is already correct on UNION ALL sources (probe: SeasonalNaive on the s2/uv fixture, EXCEPT ALL against the ut result empty both ways) and parallel across groups (1M-row panel Theta 0.112 s at default threads vs 0.935 s at threads = 1; Naive 0.072 s vs 0.444 s). Its body must not change.
- No macro calls `_ts_forecast_native`; only test/sql/ts_forecast_param_grid.test, test/sql/ts_native_model_names.test and test/sql/ts_native_param_validation.test call it directly, positional (TABLE, horizon INTEGER, frequency VARCHAR, method VARCHAR, params ANY). On the uv fixture, `_ts_forecast_native((SELECT id, ds, y FROM uv), 3, '1d', 'Naive', MAP{})` gives 9 rows, sum(yhat) 484.871756; on the materialized table ut 548.917583 (partial input; reproduced 3/3 runs).
- _ts_forecast_native fits all groups serially inside its finalize (ts_forecast_native.cpp ~line 626 loop), as every collect-then-finalize native does, so fitting parallelism is unaffected by the barrier; only intake was parallel and stays parallel with TsCollectFinalizeBarrier.
- Measured costs on the 1M-row panel (default threads): _ts_forecast_native Naive 0.396 s; with a MATERIALIZED CTE input 0.551 s (+0.155 s); ts_mae_by 0.228 s; ts_stats_by 2.944 s.
- Registrations: `ts_aggregate_hierarchy(TABLE, MAP(VARCHAR, VARCHAR))` (map keys separator default '|', aggregate_keyword default 'AGGREGATED'); `ts_split_keys(TABLE, separator := VARCHAR, columns := LIST(VARCHAR))` (separator default '|', columns optional); `ts_validate_separator(TABLE, separator := VARCHAR)` (default '|'). None registers an anofox_fcst_ alias. Bind code skips a NULL named parameter only when `kNamedParamsHaveNullDefault` (DuckDB 2.0); with a macro passing `columns := NULL` the natives must skip NULL named values on every DuckDB line.
- RegisterTsTableMacros (src/macros/ts_macros.cpp) registers an `anofox_fcst_<name>` alias for every ts_table_macros[] entry; a public macro gaining that alias is acceptable (consistent with every other macro), but an underscore-internal name must not get one.
- A macro and a table function cannot share a name: the C++ functions are renamed to `_ts_aggregate_hierarchy_native`, `_ts_split_keys_native`, `_ts_validate_separator_native`, `_ts_forecast_native_impl`.
- Call sites to keep working: test/sql/ts_multi_key.test, test/sql/ts_aggregate_hierarchy.test, test/sql/correctness/data_prep.test, the three _ts_forecast_native test files, docs/api/02-hierarchical.md, docs/api/01-table-macros.md, examples/multi_key_hierarchy/*, examples/data_preparation/null_handling_examples.sql, the data-prep SKILL.md (all exercised by the full suite and make check-docs).
