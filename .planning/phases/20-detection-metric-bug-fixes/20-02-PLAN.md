## Planner-verified facts (2026-10-23, build/release at 9d11361, DuckDB v2.0.0, 20 cores)

- #285 setup: `CREATE TABLE s AS SELECT id, (TIMESTAMP '2024-01-01' + INTERVAL (i) DAY) AS ds, base + 0.3 * i + 5 * sin(2 * pi() * i / 7) + CASE WHEN id = 'B' AND i >= 50 THEN 15 ELSE 0 END + 1.6 * cos(i * 0.9) + 0.7 * sin(i * 1.7 + base) AS y FROM (VALUES ('A', 20.0), ('B', 40.0), ('C', 60.0)) t(id, base), range(84) r(i); CREATE TABLE f AS SELECT id, ds, y, y + 1 AS yhat FROM s WHERE ds >= TIMESTAMP '2024-03-11';`
- On this build BOTH the literal cut-off and the scalar-subquery cut-off shapes return NULL for A/B/C (also with `SET threads = 1`); the issue body saw only the subquery shape fail. Which branch finishes first is plan- and version-dependent, so tests cover both shapes plus reversed and shuffled.
- `ts_mae_by((SELECT id, ds, y, y+1 AS yhat FROM s WHERE ds < TIMESTAMP '2024-02-01' UNION ALL SELECT id, ds, y, y+3 FROM s WHERE ds >= (SELECT min(ds) FROM f)), 'ds', 'y', 'yhat')` returns exactly 1.0 per group: only the first branch reached the computation (the all-rows MAE is (31*1 + 14*3)/45).
- Multi-pipeline mechanism (DuckDB v2.0.0, duckdb/ submodule): a UNION ALL below an operator creates two pipelines sharing the operator's global state (src/parallel/pipeline.cpp ResetSinkAndOperators creates op_state once), and PipelineExecutor calls FinalExecute (our in_out_function_final) at the end of EACH pipeline (src/parallel/pipeline_executor.cpp ~line 169-198). The natives' finalize_claimed / threads_collecting barrier only waits for threads already registered in InOut, so the first finishing pipeline emits results on partial data.
- Proven fix for the multi-pipeline part: `SELECT * FROM (WITH src AS MATERIALIZED (<#285 subquery-cutoff UNION ALL>) SELECT * FROM _ts_mase_native((SELECT * FROM src), 'ds', 'y', 'yhat', 7))` returns A 0.4764952155298452, B 0.26551450050730596, C 0.4759518449064799 (a materialized CTE scan is one pipeline).
- A table macro cannot write `FROM source` when `source` is a subquery argument (Catalog Error: Table with name source does not exist); parameters substitute only in expression positions such as a table-function argument. Hence `_ts_passthrough(source)`: a streaming identity in-out function with no in_out_function_final (correct under any number of pipelines).
- Intra-pipeline race and why not MaxThreads 1: inside one pipeline, a thread that receives no chunk can reach the final before another thread's first InOut registered it, so the old barrier can finalize early. Reducing the pipeline to one executor fixes that but serializes intake: measured on a 1M-row panel (5000 series x 200 days), `SET threads = 1` vs default gave _ts_forecast_native Naive 0.553 s vs 0.396 s and ts_mae_by 0.433 s vs 0.228 s. The fix that keeps parallel intake: DuckDB's PipelineExecutor constructor creates every operator local state (our init_local) before it fetches any source data (pipeline_executor.cpp constructor, `GetOperatorState` loop), so any executor that holds rows has already called init_local. A barrier that counts init_local calls and final arrivals and lets the arrival that makes them equal do the processing (no spin-wait) is complete within one pipeline; executors created later hold no rows (the source is exhausted) and return FINISHED.
- The materialized CTE itself costs about 0.15 s per 1M rows (_ts_forecast_native Naive 0.396 s -> 0.551 s at default threads). 20-05 measures this against a baseline binary.
- Every native does its Rust work single-threaded in finalize already (each in-out native's anofox_* calls sit after its finalize function start), so the barrier change affects only intake.
- The metric natives in src/table_functions/ts_metrics_native.cpp: _ts_metrics_native (ts_mae_by, ts_mse_by, ts_rmse_by, ts_mape_by, ts_smape_by, ts_r2_by, ts_bias_by), _ts_mase_native (ts_mase_by), _ts_rmae_native (ts_rmae_by), _ts_coverage_native (ts_coverage_by), _ts_quantile_loss_native (ts_quantile_loss_by); macro bodies at src/macros/ts_macros.cpp ~2429-2575, each `SELECT * FROM _ts_..._native(source, ...)`.
- R MASE reference: validation/reference/r/gen_mase_reference.R writes r_mase/accuracy_mase.json (cases keyed by name, mase_accuracy and mase_manual), consumed by crates/anofox-fcst-core/tests/metrics_reference.rs; `Rscript validation/reference/r/gen_mase_reference.R` works locally.
